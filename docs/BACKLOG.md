# بک‌لاگ ویژگی‌ها

این فایل **تنها مرجع** کارهای این پروژه است. هر ویژگی یک شناسه می‌گیرد، از یک
مسیر ثابت عبور می‌کند، و تا وقتی در جدول وضعیت «تحویل‌شده» نشده، تمام نیست.

## وضعیت‌ها

| نشان | معنی |
|---|---|
| 📥 `inbox` | ثبت شده، هنوز بررسی نشده |
| 📝 `spec` | مشخصات نوشته شده، منتظر تأیید |
| 🔨 `building` | در حال پیاده‌سازی |
| 🧪 `verify` | پیاده شده، در حال تست |
| ✅ `done` | تست شده، push شده |
| ⏸️ `blocked` | منتظر تصمیم یا اطلاعات |

## قالب هر ویژگی

وقتی یک درخواست می‌رسد، این بلوک را زیر جدول اضافه می‌کنم و پر می‌کنم:

```md
### F-001 — <نام ویژگی>

**درخواست اصلی:** <نقل قول کاربر، بدون تغییر>

**چه چیزی می‌سازیم:** <۲–۳ جمله به زبان کاربر، نه زبان کد>

**تعریف «تمام شد»:**
- [ ] <رفتار قابل مشاهده ۱>
- [ ] <رفتار قابل مشاهده ۲>
- [ ] روی موبایل ۳۹۰px درست کار می‌کند
- [ ] روی دسکتاپ ۱۴۴۰px درست کار می‌کند

**تغییرات فنی:**
- دیتابیس: <مدل/فیلد جدید یا «هیچ»>
- API: <مسیر جدید یا «هیچ»>
- UI: <کامپوننت/صفحه>
- ماژول: <ثبت جدید یا «هیچ»>

**لبه‌ها و خطاها:**
- <حالت خالی / ورودی نامعتبر / دسترسی / داده زیاد>

**تست:**
- واحد: <چه چیزی>
- دستی: <مسیر کلیک>

**ریسک:** <چه چیزی ممکن است بشکند>
```

## چرا این ساختار

سه چیز را حل می‌کند:

1. **فراموشی** — هر درخواست یک شناسه دارد؛ بین نشست‌ها گم نمی‌شود.
2. **پراکندگی** — «تعریف تمام‌شد» مانع می‌شود چیزی نیمه‌کاره تحویل شود.
3. **تاب‌آوری** — عامل بعدی فقط این فایل را می‌خواند و می‌داند کجاست.
